# ParamSpec / TypeVarTuple `variables`: scoping brief (#1621)

Status: scoping brief for the implementing agent. Docs-only; no production
code in this PR.
Date: 2026-09-14. Head: `656cddbe3` (`origin/main`).
Issue: #1621 (`mass migration: ParamSpec/TypeVarTuple variables channel (573 solve defers)`).
Parent: #1625 (master plan).

## 1. Read this first: two of the four proposed steps are already done

The issue's premise is that the kernel has no representation for callable
`variables`. **That is wrong.** Both of its first two fix-direction steps
shipped in earlier waves. Do not spend effort re-adding them.

### 1.1 The wire `CallableType` already carries `variables`

- Field: `crates/type_kernel/src/wire.rs:639` (`pub variables: Vec<Type>`),
  written at `crates/type_kernel/src/wire.rs:2395`
  (`write_type_var_likes(buf, &p.variables)`).
- Reader: `crates/type_kernel/src/wire.rs:855-881`
  (`read_type_var_likes`), which dispatches all three kinds:
  `TYPE_VAR_TYPE`, `PARAM_SPEC_TYPE`, `TYPE_VAR_TUPLE_TYPE`.
- Decoded into the Rust enum at `crates/type_kernel/src/wire.rs:1085-1093`
  and `:1210-1229`.
- Already read by the kernel for a real decision: `is_generic`-style check at
  `crates/type_kernel/src/types_impl.rs:654-668`.

So a ParamSpec or TypeVarTuple in `callee.variables` is visible to Rust today.
`_serialize_type_for_checkexpr(callee)` at the call sites already transmits it.

### 1.2 `new_unification_variable` semantics are already ported

- Python: `mypy/types.py:793-796`
  (`new_unification_variable` = `old.copy_modified(id=TypeVarId.new(meta_level=1))`),
  called from `mypy/expandtype.py:796-804`.
- Rust: `crates/type_kernel/src/freshen.rs:663-691` (the freshen loop, with
  the default cross-referencing rule at `:678-684`) and
  `crates/type_kernel/src/freshen.rs:722-800` (`fresh_type_var`), which
  handles `TypeVarType`, `ParamSpecType` **and** `TypeVarTupleType`, keeping
  every field and re-issuing `(raw_id, meta_level=1, namespace="")`.
- Landed in wave-62C (#1518), whose entry records the generalization
  explicitly. `var_env_key` (`freshen.rs:700-718`) keys all three kinds.

Aside: the docstring at `crates/type_kernel/src/freshen.rs:722` cites
`types.py:770-772` for `new_unification_variable`. The real anchor is
`mypy/types.py:793-796`; 770-772 is inside `TypeVarType.__init__`. Fix the
comment when touching the file.

**Conclusion: #1621 is a semantics problem about the substitution and
constraint engines, not a wire-format problem.** The whole of the remaining
work is in `expandtype.rs`, plus the gate removals that the current defers
exist to protect.

## 2. The real defer inventory

Counts are from the wave-48b audit of `rust_solve_generic_call` (issue #1462,
generated by env-gated instrumentation that was stripped before landing, and
reproduced in `AGENTS.md`). Note that these are **wrapper-level gate events**,
not kernel decisions: the Python shim counts how often it declines to enter
the kernel.

| Defer | Count | Gate anchor | Root cause |
|---|---|---|---|
| `lam_typevar` | 463 | `mypy/checkexpr.py:3124-3136` | A lambda actual whose inference context type mentions one of the callee's own type variables. |
| `need_refresh` | 90 | `mypy/checkexpr.py:3085-3087` | The callee's `variables` contain a `ParamSpecType` or `TypeVarTupleType`. |
| `var_pspec_tvt` | 80 | `crates/type_kernel/src/solve.rs:1948-1963` | Kernel-side counterpart of `need_refresh`, at the ifta entry. |
| applytype TVT splice | small | `crates/type_kernel/src/applytype.rs:161-176` | A TypeVarTuple variable receives a TVT or a tuple target. |
| constraints ParamSpec kinds | small | `crates/type_kernel/src/constraints.rs:1059-1061` (`kind == 1`), `:2637-2643` | `Parameters` slicing on the `ParamSpecType` actual. |

The issue's arithmetic is off by 20: 463 + 90 = 553, and the issue quotes both
553 (in "Affected seams") and 573 (title and Impact). Use **553 wrapper-level
events**, of which only `need_refresh` + `var_pspec_tvt` + the two small
entries are candidate retirements.

### 2.1 `need_refresh` (90 events)

Python gate, `mypy/checkexpr.py:3085-3087`:

```python
need_refresh = any(
    isinstance(v, (ParamSpecType, TypeVarTupleType)) for v in callee.variables
)
```

Kernel-side counterpart, `crates/type_kernel/src/solve.rs:1948-1963` and
`crates/type_kernel/src/checkcall.rs:854-865` (both cite
`constraints.py:475-494`, `filter_imprecise_kinds`). The kernel comment at
`checkcall.rs:860` says "expand_type defers", and that is the actual wall:

- `crates/type_kernel/src/expandtype.rs:11`: "TypeVarTuple substitution
  requiring `split_with_prefix_and_suffix` (the variadic middle of a generic
  instance)". Python reference: `mypy/expandtype.py:692-708`, which splits
  `instance.args` with `split_with_instance`, splits
  `instance.type.defn.type_vars` with `split_with_prefix_and_suffix`, and
  binds `tvar.id -> TupleType(list(args_middle), tvar.tuple_fallback)`.
- `crates/type_kernel/src/expandtype.rs:17`: "`visit_callable_type` ParamSpec
  splices carrying an UnpackType result (Python's `normalize_trivial_unpack`
  is not ported)". Python reference: `mypy/expandtype.py:1173-1195`.
- `crates/type_kernel/src/expandtype.rs:26-29`:
  `visit_type_var_tuple` (`mypy/expandtype.py:1091-1104`) raises
  `NotImplementedError` in Python for a replacement that is neither a
  `TypeVarTupleType` nor `Any`/`Never`; the kernel defers instead of raising.

**What must change**: port the variadic-middle env binding and the
Unpack-carrying ParamSpec splice in `expandtype.rs`, then lift the two guards
(`solve.rs:1948-1963`, `checkcall.rs:854-864`) and the Python gate
(`checkexpr.py:3085-3087`) in the same commit. Nothing in `solve.rs`'s own
solve logic is ParamSpec-specific beyond those guards.

Risk: **high, and it is a known crash class.** The variadic middle is the
shape that produced the wave-33 recursive-alias segfault through
`make_simplified_union`/`is_subtype`/`tuple_fallback`, and #1511 had to fix a
latent `with_normalized_var_args` divergence where the TypeVarTuple branch
pushed a bare `TypeVarTupleType` instead of the enclosing `UnpackType`
(`mypy/types.py:2608-2610`). Treat the splice as a parity-critical change:
land it with the gate still closed, prove gate-off versus gate-on byte
parity on testcheck, and only then flip.

### 2.2 `lam_typevar` (463 events): a seam restructure, not a floor

Python gate, `mypy/checkexpr.py:3124-3136`. A lambda actual whose context type
contains one of the callee's type variables cannot be accepted with that
context, so the shim bails out of the whole native solve and Python runs
`infer_function_type_arguments` (`mypy/checkexpr.py:3650-3760`) including the
two-pass path (`mypy/checkexpr.py:3850-3919`).

The wave-48b audit classified this as "a full algorithm not a decision", and
on the current seam shape that is right: the lambda's type comes from
`visit_lambda_expr`, which needs live expression checking, and Rust cannot
produce it. **But the classification hides a decidable sub-case.**

Python's own pass 1 does not need the lambda type. In
`mypy/checkexpr.py:3680-3686` it builds `pass1_args` with `None` for every
actual whose pass number is 2, and the pass numbers come from
`get_arg_infer_passes` (`mypy/checkexpr.py:3926+`), which is **already
ported** (`rust_get_arg_infer_passes`, issue #1000). So for exactly the
actuals this gate bails on, Python's pass 1 substitutes `None`. A shim that
did the same, then let Rust solve pass 1 and handed the result back to
Python for `infer_function_type_arguments_pass2`
(`mypy/checkexpr.py:3850-3919`) plus the `need_refresh` formal-to-actual
recalculation (`mypy/checkexpr.py:3206-3216`), would be semantically
equivalent to what Python does today.

**What must change**: split the seam. `rust_solve_generic_call`
(`crates/type_kernel/src/checkcall.rs:800+`) currently does solve *and* apply
in one call. The split needs (a) a pass-1-only entry that returns the
inferred argument list, and (b) Python to run pass 2 and the apply half.
`rust_infer_function_type_arguments` (`crates/type_kernel/src/solve.rs:1917`)
is already a pass-1 entry returning an optional-type list blob, so the
primitive exists; what does not exist is the Python-side driver that consumes
it mid-`check_call`.

Risk: **medium-high, and the first step is a spike, not an implementation.**
Before any Rust change, prove on the corpus that Rust pass 1 with `None` for
every pass-2 actual reproduces Python's own pass-1 inferred args exactly
(the #1455-framing lesson: a seam that returns the right *shape* but a
different list is worse than a defer). Do this as a differential test against
`infer_function_type_arguments` with the kernel off.

Note also the adjacent conservative gate at `mypy/checkexpr.py:3696-3703`
(`2 not in arg_pass_nums`) which refuses the native ifta whenever any pass-2
actual exists. Same reasoning applies; it is the same spike.

### 2.3 Small entries

- `crates/type_kernel/src/applytype.rs:161-176`: defers when any target is a
  `TypeVarTupleType`, or when a TVT variable receives a tuple. Python's rule
  is looser in `get_target_type` (`mypy/applytype.py:343-346` returns the
  target unchanged for ParamSpec and TVT tvars) and the real difficulty is
  again the env substitution in `expandtype.rs`. Fold this into the section
  2.1 slice, do not treat it separately.
- `crates/type_kernel/src/constraints.rs:1059-1061` (`kind == 1`,
  `ParamSpecType`, "defer (needs Parameters slicing)") and `:2637-2643`
  (ParamSpec/TVT in the callee's `variables`). The surrounding ParamSpec
  machinery is already substantial (`param_spec_of` at `:3130-3160`, the
  prefix branch at `:3008-3100`, ParamSpec-to-ParamSpec at `:2843`), so these
  two are the residues. Fold into 2.1.

## 4. Floors (do not attempt)

1. `ExpandTypeVisitor.visit_type_var_tuple`'s `NotImplementedError`
   (`mypy/expandtype.py:1091-1104`) for a replacement that is neither a
   `TypeVarTupleType` nor `Any`/`Never`. Python **raises**; callers catch it
   (`except (NotImplementedError, AssertionError)` appears throughout
   `mypy/expandtype.py` and `mypy/checkexpr.py`). Porting a raise across FFI
   buys nothing and changes the failure taxonomy.
2. `PolyTranslationError` paths (`mypy/applytype.py:640-660`). That is the
   polymorphic-inference machinery (`poly_tvars` / `bound_tvars`), a
   subsystem in its own right; it is not a `variables`-channel item.
3. The lambda *body* type itself. It comes from `visit_lambda_expr`, i.e.
   live expression checking. No wire addition reaches it.
4. `need_refresh`'s formal-to-actual recalculation
   (`mypy/checkexpr.py:3206-3216`) needs `self.accept(args[i])`, so it stays
   Python under any version of rank 2.

## 5. Seam shape, gate, registrar discipline

- **Gate**: reuse `Options.native_type_kernel` and the existing per-call
  gates (`_native_checkexpr_active`, `_native_checkexpr_resolver`). No new
  option, no new `OPTIONS_AFFECTING_CACHE` entry.
- **Defer contract**: `None` defers the whole call; map only
  `PyAttributeError` to a defer and let everything else propagate (the
  #1466/#1468 narrowing rule). A fresh-var-bearing decoded tree must stay out
  of any shared decode cache (the #1180/#1198 rule) and must go through
  `canonicalize_fresh_vars` (issue #1180) plus the wirefixup identity repair
  (`resync_var_identities`, issue #1215) on the way back.
- **Registrar**: no new registrar. The solver resolver is installed by
  `_build_native_resolvers` and cleared per build and per daemon recheck
  through `BuildManager._clear_native_resolvers`; the variadic-middle port
  reads the same snapshot the existing expand arms read (`TypeResolver`
  alias view, `install_aliases`).
- **Wire format**: unchanged. No `CACHE_VERSION` bump: `variables` is
  already in the persistent wire format and its layout must not change.
- **Rebuild discipline**: any `crates/type_kernel/src/*.rs` edit requires
  rebuilding the `.so` into a private scratch dir and putting it on
  `PYTHONPATH` (see the "Type kernel build order" section of `AGENTS.md`).
  Never `maturin develop`.

## 6. Test plan

For rank 1:

- Rust unit tests in `expandtype.rs` for the variadic-middle binding: a
  generic class with a TVT in the middle expands to the `TupleType` binding;
  prefix and suffix bind normally; the TypeVarTupleType-to-itself case takes
  the identity branch (`mypy/expandtype.py:1091-1100`); the Unpack-carrying
  ParamSpec splice produces the ARGS/KWARGS pair.
- `NativeSolveGenericCallSuite` and `NativeConstraintsDeferralSuite` in
  `mypy/test/testtypes.py`: direct seam calls for a ParamSpec callee and a
  TVT callee, proving the guards no longer fire, plus the existing defer pins
  re-expressed as engagement pins where the guard is removed.
- Gate-off versus gate-on differentials on `str(result)` and captured error
  messages, following the established `Native*Suite` pattern.
- testcheck gate-off versus gate-on parity: zero diff (local baseline 8,144
  passed / 69 skipped / 7 xfailed; CI skips fewer cases for environment
  reasons).
- Cold self-check: 0 errors, and the recorded defer counts for
  `need_refresh` / `var_pspec_tvt` re-measured with the same stripped
  instrumentation and reported in the PR body.

For rank 2 (only if the spike passes):

- The spike itself: a differential test that calls Python's
  `infer_function_type_arguments` with the kernel off and compares its
  pass-1 `inferred_args` against the Rust pass-1 list on the same call, over
  the testcheck corpus. Report the mismatch count in the issue before
  implementing.
- Then `NativeSolveGenericCallSuite` cases for a lambda actual with a
  tvar-bearing context, plus the testcheck differential and the self-check.

1. Fix-direction step 1 ("Add a `variables` wire field") is already shipped:
   `crates/type_kernel/src/wire.rs:639`, reader at `:855-881`.
2. Fix-direction step 2 ("Port `new_unification_variable` semantics") is
   already shipped for all three kinds:
   `crates/type_kernel/src/freshen.rs:722-800`, landed in #1518.
3. The count is 553, not 573 (463 + 90). The kernel's own `var_pspec_tvt`

   be added to it; it is the kernel-side event for the same gate.

   defers. The defers are Python-side gate events at `mypy/checkexpr.py:3085`
   and `:3134`; the kernel-side guards are in `crates/type_kernel/src/solve.rs:1948`

   `crates/type_kernel/src/expandtype.rs`, which the issue does not list.

   not: ParamSpec and TypeVarTuple `variables` freshen natively as of #1518.
